# Frontend: Kanban Studio

Kanban board UI. As of Part 3, `next.config.ts` sets `output: "export"` and the Docker build compiles this into static HTML/JS served by FastAPI at `/` (see backend/AGENTS.md) — no `next dev`/Node server needed at runtime. As of Part 4, the backend gates `/` and `/login` by session cookie, so all auth/redirect logic lives server-side — the frontend just posts credentials and lets the backend decide where to send the browser next. As of Part 7, board state is no longer local — it's fetched from and mutated through the Part 6 API, backed by the real SQLite DB.

## Stack

- Next.js 16 (App Router), React 19, TypeScript
- Tailwind CSS 4 (via `@tailwindcss/postcss`), styled with CSS variables in `globals.css`
- `@dnd-kit/core` + `@dnd-kit/sortable` for drag and drop
- Vitest + Testing Library for unit/component tests, Playwright for e2e
- `clsx` for conditional class names

## Structure

- `src/app/layout.tsx` — root layout, loads Google fonts (Space Grotesk for display, Manrope for body), sets page metadata
- `src/app/page.tsx` — renders `<KanbanBoard />` at `/`
- `src/app/globals.css` — Tailwind import + the CLAUDE.md color palette as CSS variables (`--accent-yellow`, `--primary-blue`, `--secondary-purple`, `--navy-dark`, `--gray-text`)
- `src/lib/kanban.ts` — domain types (`Card`, `Column`, `BoardData`), `initialData` (kept only as canned board data for tests — no longer the runtime seed), `columnAccentColor(columns, columnId)` (assigns each column one of the 5 CLAUDE.md palette colors by its *position*, not its title, so renaming a column never changes its color and the mapping never needs new colors invented), and the pure helper `moveCard` (reorder/relocate cards by id, used for both same-column reorder and cross-column drop — still used client-side to compute the optimistic UI state before/independent of the API round-trip)
- `src/components/KanbanBoard.tsx` — top-level stateful component. `board` starts `null` and is populated by `GET /api/board` on mount (loading/error states render in its place until then). Every mutation (`handleDragEnd` → move, `handleRenameColumn`, `handleAddCard`, `handleDeleteCard`) goes through `runMutation`: apply an optimistic local update immediately, fire the API call, replace `board` with the server's authoritative response on success, or roll back to the pre-mutation `board` and show `actionError` (`data-testid="board-error"`) on failure. `<main>` has no max-width (`w-full`) — the board uses the full viewport. The columns section is `grid grid-cols-[repeat(5,minmax(220px,1fr))]` — 5 equal-width columns that flex to fill whatever width is available (no wasted space, no scrollbar on any normal desktop viewport), with a 220px floor so they never get uselessly thin; `overflow-x-auto` stays on as a fallback for viewports narrower than that floor can support, but it won't trigger on typical screens. `ChatSidebar` is rendered here too, but it's `fixed`-positioned and floats over everything — it takes no layout space at all, which is why the columns don't need to make room for it (first pass had it in-flow as a permanent sidebar, which is what caused the squeeze in the first place — see git history; second pass used a fixed-px column width, which fixed the squeeze but reintroduced a scrollbar on narrower screens since 5×264px+gaps doesn't fit most laptop viewports — this grid-with-a-floor approach is the one that stuck).
- `src/components/KanbanColumn.tsx` — droppable column; fills its grid cell (no width class of its own — sizing is entirely the parent grid's job, see `KanbanBoard.tsx` note above). Takes an `accentColor` prop (from `columnAccentColor`) used for its header bar and the `isOver` drop-target highlight (applied via inline `style`, not a Tailwind class, since the color is data-driven per column, not one of a fixed set of utility classes). Title `<input>` buffers edits in local `titleDraft` state (so typing doesn't fire a request per keystroke) and only calls `onRename` on blur or Enter; renders cards in a `SortableContext`, embeds `NewCardForm`
- `src/components/KanbanCard.tsx` — sortable/draggable card with a delete button
- `src/components/KanbanCardPreview.tsx` — static (non-interactive) card rendering used inside `DragOverlay` while dragging
- `src/components/NewCardForm.tsx` — toggle button that expands into a title+details form; calls `onAdd` and closes itself on submit
- `src/app/login/page.tsx` — renders `<LoginForm />`; static export produces `out/login.html`
- `src/components/LoginForm.tsx` — username/password form; `POST /api/login`, shows a `data-testid="login-error"` message on failure, calls `onSuccess` (defaults to `window.location.href = "/"`) on success — the `onSuccess` prop exists purely so unit tests can assert without a real navigation
- `KanbanBoard.tsx`'s header also has a "Log out" button: `POST /api/logout` then `window.location.href = "/login"`
- `src/components/ChatSidebar.tsx` — AI chat as a floating, collapsible widget (`fixed bottom-6 right-6`), not an in-page sidebar. `isOpen` (local state, default `false`) toggles between two entirely different renders: minimized is just a round purple FAB (`data-testid="chat-toggle"`) with a chat-bubble icon; expanded is the full panel — header with a minimize button (`data-testid="chat-minimize"`) plus the same chat UI as before. Owns its own `messages` history (not lifted to `KanbanBoard`); on send, `POST /api/ai/chat` with `{board, message, history}` and appends the reply. No optimistic update for the board — unlike the drag/rename/add/delete mutations, there's no way to predict what the AI will do, so it just calls `onBoardUpdate(data.board)` (wired to `KanbanBoard`'s `setBoard`) with the server's authoritative response once it arrives. Test hooks: `data-testid="chat-toggle"`/`"chat-minimize"`/`"chat-input"`/`"chat-send"`/`"chat-messages"`/`"chat-message-user"`/`"chat-message-assistant"`/`"chat-error"` — anything that interacts with the chat has to click `chat-toggle` first, it's minimized by default. Its `<h2>` is deliberately "Chat with the assistant", not anything containing "Kanban Studio" — the board header's `<h1>Kanban Studio</h1>` is elsewhere on the same page and `getByRole("heading", {name: "Kanban Studio"})` substring-matches by default, so a second heading containing that phrase breaks existing tests with a strict-mode violation (hit this once — see git history).

## State shape

`BoardData = { columns: Column[]; cards: Record<string, Card> }`, matching `docs/schema.json`'s API response shape exactly (column ids are the DB's `slug`, card ids are `card-<db-id>`) — the frontend does zero id translation.

## Data flow

All mutation logic lives in `KanbanBoard.tsx` and is passed down as callback props — child components never call `fetch` themselves (except `LoginForm`'s login call and the logout button, which are one-shot and don't need board state). `moveCard` in `lib/kanban.ts` stays a pure function (columns in, columns out) so it's unit-testable without rendering, and is reused to compute `handleDragEnd`'s optimistic update.

## Testing

- Unit/component: `npm run test:unit` (Vitest, jsdom) — `src/lib/kanban.test.ts` covers `moveCard` logic in isolation; `src/components/LoginForm.test.tsx` covers the wrong-password and correct-password paths by mocking `fetch` and passing `onSuccess`; `src/components/KanbanBoard.test.tsx` mocks `fetch` with a small in-memory fake server (see `createFakeServer` in that file) so it exercises the real load/mutate/reconcile flow — covers initial load, load failure, rename, add+delete, and a mutation-failure rollback case; `src/components/ChatSidebar.test.tsx` mocks `fetch` directly (no fake server needed, single endpoint) and covers the empty-state hint, a full send→reply→`onBoardUpdate` round trip (asserting the exact `POST /api/ai/chat` body), and the request-failure error path
- E2E: `npm run test:e2e` (Playwright) — `tests/kanban.spec.ts` covers board load, adding a card, drag-and-drop between columns (`data-testid="column-*"` / `data-testid="card-*"` are the drag/drop test hooks — keep them when refactoring), and a reload-persistence test (add a card, wait for the POST response, `page.reload()`, confirm it's still there — proves persistence through the real backend/DB, not just client state); `tests/login.spec.ts` covers the unauthenticated-redirect, wrong-password, full login→board→logout, and authenticated-visits-to-/login-redirect flows; `tests/ai-chat.spec.ts` is a *live* test — clicks `chat-toggle` to expand the widget, types a request, waits for a real assistant reply, confirms the board visibly updates, then clicks `chat-minimize` and confirms it collapses back (deliberately an *add-card* request, not move, so it can't collide with `kanban.spec.ts`'s card-1 assumptions — see the shared-DB note below). `tests/auth.ts`'s `loginViaApi` logs in via `page.request.post("/api/login")` (cookies land in the browser context) so `kanban.spec.ts`'s `beforeEach` can skip the UI and get straight to an authenticated board.
- `npm run test:all` runs both — this is the single documented command for the full frontend suite

**Drag test picks adjacent columns on purpose**: `kanban.spec.ts`'s drag-and-drop test drags `card-1` from `col-backlog` into `col-discovery` (its immediate neighbor), not a further column like `col-review`. All 5 columns fit within a normal viewport now (see the grid note above), so this mostly doesn't matter today — but the columns row can still scroll horizontally on a genuinely narrow viewport, and a raw two-point mouse simulation (`mouse.move` → `mouse.down` → `mouse.move` → `mouse.up`) can't drag between two columns that aren't *both* visible at once: scrolling the target into view first just pushes the source card off-screen instead, since dnd-kit's auto-scroll-while-dragging isn't triggered by a simulated two-point move. Tried dragging to a far column under the old fixed-width layout and reverted it — not worth simulating real auto-scroll for something the plan didn't ask for. Keep new drag tests to adjacent columns as a matter of habit, since it costs nothing and stays robust regardless of viewport width.

**Shared-DB gotcha for new e2e tests**: every spec file in one `npm run test:e2e` run shares the same backend container and SQLite DB (only wiped once, at the start of the whole run — see the lifecycle note below), and Playwright runs spec files in parallel workers by default. A test that *moves or deletes* a pre-existing seed card (e.g. `card-1`) can race with another spec's assumptions about that same card's position. Prefer additive actions (add a card with a unique title) when the specific card/column touched isn't the point of the test; if a test must move/delete seed data, give it sole ownership of that card or accept it needs `test.describe.serial` / a dedicated card.

E2E lifecycle: `playwright.config.ts` uses `globalSetup`/`globalTeardown` (`tests/global-setup.ts` / `tests/global-teardown.ts`), not `webServer`. Setup runs `docker compose down`, deletes `backend/data` (so every run starts from a freshly-seeded DB — otherwise state would accumulate across runs and the reload-persistence/move tests would become order-dependent), then `docker compose up --build -d` and polls `/api/health`. Teardown runs `docker compose down` unconditionally. This also sidesteps the earlier `webServer`-based approach's flaky container-leak-on-Windows problem, since Node's `execSync` control flow doesn't depend on signal propagation to a spawned shell process.
